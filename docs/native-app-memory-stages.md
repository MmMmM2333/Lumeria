# 完整 native 应用内存增量与需求解码调查

2026-09-10，基线f4a3d17 / Starter0.3.4 / Bun1.4.2。本轮仅隔离诊断，产品无实现改动。

## 方法

复用旧合成夹具：190个独立256×256 PNG（纯色，编码总计约0.16MiB）、36文件夹、3页、
图标128。另派生空布局、无图片占位组、190图片平铺组；没有复制真实用户布局或应用信息。
900×600/DPI1、无系统材质、相同后台设置与加载并发4。所有图标及设置操作留在隔离目录。
通过本地构建插件在初始化边界记录内存，产品源码不注入探针。阶段以Windows页属性记录
私有驻留/提交，同时记录JSC heap/external、场景节点、图片CPU像素、文字与池预算。

开始到首场景的阶段不强制GC；闲置后独立记录诊断GC。逐页浏览后，再打开/关闭设置3次，
每次关闭单独记录GC后状态。采样本身含同步页扫描和诊断对象，有扰动，不用于启动性能结论。
表中驻留均为主Bun进程私有工作集，不含launcher与Rust数据子进程，不能直接混入上轮整组表。

| 原生窗口创建后 | 157.31 | 475.82 | 19.96 |
| 数据宿主连接/布局构建后 | 169.98 | 535.84 | 20.73 |

完整应用的模块、初始化和基础界面已产生显著成本，未放应用图标时也不是最小窗口。

最小窗口和完整bundle导入模块不同且GC时序不同，不将两组每阶段简单相减成精确所有权。

## 图片与场景的增量

首屏闲置、诊断GC后：

| 夹具 | 私有驻留 MiB | JSC堆 MiB | 图标CPU RGBA MiB | 节点 / Text |
|---|---:|---:|---:|---:|
| 空布局 | 185.11 | 28.33 | 0 | 114 / 15 |
| 190占位项＋36文件夹，无图片 | 244.74 | 38.95 | 0 | 1911 / 528 |
| 190图片平铺，无文件夹 | 281.66 | 75.13 | 37.00 | 1527 / 393 |
| 190图片＋36文件夹 | 288.00 | 65.90 | 25.75 | 1911 / 528 |

全布局图片解码完成但场景尚未显示时，190图片CPU RGBA恰为47.5MiB，私有驻留从约189
增加到290MiB，external约104MiB。独立“解码后立即GC”实验：external102.45→60.30MiB，
RGBA仍47.5MiB，说明约42MiB为此时可回收的临时外部对象；私有驻留仅286.76→285.85MiB，
并未随着对象回收立即归还页面。不能用定时GC替代降低解码工作量和瞬时分配。

文件夹预览已经用Container+Sprite+Text组成，没有为每个缩略图再创建完整IconNode。
但IconNode构造时预建编辑按钮、缺失标记、标签过渡、文件夹相关控件等；文件夹预览还至少
预分配9个位置，邻页也保留真实场景。节点数量不是全部活跃GPU纹理数量：当前图片文件夹
组首屏活跃文字纹理约1.22MiB，Canvas池0.18MiB，不能把528个Text说成几百MiB位图。

## 三个排除性实验

- **只保留当前页场景**：首屏节点1911→813、Text528→204，但RGBA25.75→42.25MiB。
  因为全布局依然解码，离屏图标不能上传释放CPU像素，部分场景节省被像素保留抵消。
  私有驻留该单组288→273.88MiB。这是诊断下限，不是可部署方案，翻页效果未作等价验证。
- **隐藏标签**：节点数不变，活跃文字纹理1.22→0.15MiB，首屏私有驻留约274.25MiB。
  有一些收益，但远不足以解释全部差额，也不建议为此牺牲标签显示。
- **设置3次打开/关闭**：关闭后场景节点回原值；空布局纹理池约1.27MiB、Canvas池0.53MiB，
  图片文件夹组纹理池约1.87MiB。堆和RSS没有每次回到完全相同值，但3轮不足以证明泄漏。
  全页浏览的高驻留会在后续阶段下降，说明回收/分配器高水位对任务管理器数字影响明显。

## 需求解码：可重复的下一步方向

保持原当前页＋邻页场景、标签与控件，只将启动预加载集合限制为首两页所需图标。
此夹具启动加载87张而非190张；其他页面仍在实际场景使用时触发加载。这个诊断模式没有
完成首次远跳占位图、文件夹展开、拖拽、替换图标、设备恢复的正式行为验收，不可直接部署。

原策略与需求解码各2组：

| 阶段 | 原全量解码 | 首屏＋邻页需求解码 |
|---|---:|---:|
| 解码数量 | 190 | 87 |
| 解码阶段CPU RGBA MiB | 47.50 | 21.75 |
| 解码阶段私有驻留 MiB | 288.00–289.77 | 227.29–239.43 |
| 首屏闲置GC后CPU RGBA MiB | 25.75 | 0 |
| 首屏闲置GC后JSC堆 MiB | 65.90–65.92 | 39.73–39.75 |
| 首屏闲置GC后私有驻留 MiB | 288.00–288.36 | 265.17–267.17 |
| 首屏场景节点 / Text | 1911 / 528 | 1911 / 528 |
| 3次设置关闭后私有驻留 MiB | 311.25–312.96 | 278.15–309.71 |

首屏私有驻留可重复下降约21–23MiB，CPU RGBA少25.75MiB，且节点/标签保留一致。
逐页浏览后需求组只加载实际出现的179张，另外11张未在折叠文件夹预览中出现；全量组这11张
仍保留2.75MiB RGBA。逐页后驻留差异一度约120MiB，但设置操作后差异收敛且波动，不能承诺
长期固定节省120MiB。更可靠结论是避免不需要的解码及其临时分配，并降低首屏像素保留。

## 推荐实现顺序

1. 建立图标实际使用集合：当前/邻页、可见文件夹预览、展开文件夹、拖拽与过渡资源；在将
   新内容提交给场景之前准备纹理，复用现有beforeRender恢复机制，保证首次进入不出现占位闪烁。
   同步处理快速换页、取消、替换图标、销毁和device-lost，不只改启动时slice(0,2)。
2. 在此基础上评估冷CPU/GPU预算。只减少节点而继续全量解码会反向增加CPU保留；资源预算
   和场景保留必须一起考虑，且保留已经确认的远跳视觉效果。
3. 再看图标节点中不常用控件的延迟创建、文件夹预览占位数量及设置惰性初始化。先对真实
   使用路径量出成本，不进行与本轮无关的全面场景重写。

本轮数据来自合成PNG；真实190图标的压缩大小、尺寸、字体和文件夹内容会改变收益。
调查结论是“需求解码有明确优先级”，不是已完成产品优化。所有测试实例已退出，无用户数据修改。

证据：`.codex-dev/app-memory-stages/summary.json`，各组stages.json、阶段map.json、run.log；
build.ts/probe.ts/fixtures.mjs/summarize.py为隔离方法。首次需求构建注入位置错误，被明确拒绝，
误启动的隔离普通包已按路径确认后关闭，未纳入数据；后续两组有效样本正常完成。
