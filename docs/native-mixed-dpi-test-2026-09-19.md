# 双屏混合 DPI 实机验收（2026-09-19）

测试基线为 `5a3788c` 加工作区原有 SDK/CopySrc、toolbar 和 stress 改动。使用隔离测试数据；未修改用户布局、Windows 缩放、分辨率、屏幕排列或主屏设置。所有原始证据位于 `artifacts/mixed-dpi-2026-09-19/`。

## 环境与坐标

| 显示器 | 物理区域 x,y,w,h | 工作区 | 缩放 / DPI |
| --- | --- | --- | --- |
| DISPLAY1，主屏 | 0,0,1920,1080 | 1920×1020 | 125% / 120 |
| DISPLAY5，右侧副屏 | 1920,0,2520,1680 | 2520×1608 | 150% / 144 |

GPU：NVIDIA GeForce RTX 3060 Laptop GPU。Win32 以 Per-Monitor-V2 线程枚举，测试前后显示器配置相同。SDK 使用逻辑坐标：主屏 1536×864，副屏 x=1536、1680×1120；物理 HWND 检查使用 Win32 坐标，不能直接乘副屏原点来换算。

900×600 逻辑窗口在两屏分别对应 1125×750 和 1350×900 物理像素。测试同时比较 HWND DPI、应用公开 resolution、内容尺寸、GPU backing 像素与 GPU 子窗口尺寸，而不是只看截图。

## 已完成覆盖

独立 300 应用夹具使用各自不同的图标纹理。`matrix/proof.json` 有 40 个通过状态记录：

- 3 轮双向桌面/搜索/缓存恢复/选择迁移。搜索跨屏后结果和查询保留，清空后桌面恢复；选中 8 项后跨屏数量保持。
- 设置打开状态跨屏 4 次，布局、物理 backing 与文字密度一致。
- 两屏各测试全屏超扫 0 / 1 物理像素，外框、客户区与 GPU 子表面精确一致。开启超扫时每边扩展恰好 1 物理像素。
- 两屏分别最小化/恢复；隐藏后迁移到另一屏再显示，DPI 与 backing 更新正确。
- 两方向在应用拖拽会话进行中移动窗口，拖拽保持，继续移动与取消正常。
- 两屏分别批量创建文件夹、打开后移到另一屏、关闭恢复桌面。
- 所有可见文字密度至少为 `max(2, resolution)`；首个图标中心命中正确。

`recovery/proof.json` 另有 4 个通过记录：两个 DPI 下手动恢复原生 GPU surface 后尺寸/文字与图标命中正常，并通过真正 Windows SendInput 点击设置按钮，确认恢复后的输入链路可用。完整 smoke 另含 device-lost 注入恢复。

`extra/proof.json` 有 4 个通过记录：窗口/全屏两种模式，鼠标置于另一屏后调用产品所用的 `prepareShortcutActivation` 并显示，正确定位到目标屏、同步 DPI。每种组合执行 Windows 25 点命中覆盖，共 100 点，均未穿透到其他窗口。全屏恢复仍保持超扫物理边界。

`os-drag/proof.json` 有 4 个通过记录：真正 SendInput 拖动应用顶部拖动区跨越两屏，125% → 150% 与反向均保持约 900×600 逻辑大小（物理像素取整允许不足 1 逻辑像素差异）；分别拖动右下角调整窗口大小，GPU backing/客户区/子窗口同步，文本与图标命中正常。末次拖动抵达主屏工作区边界，Windows 将窗口纵向贴合工作区，实际逻辑高度为 816；检查采用真实客户区，而非假定拖动距离等于最终尺寸变化。

独立矩阵及补试总计 **52 个通过状态记录**，另有两屏完整 smoke 和两组性能基准；这些是当前场景检查计数，不代表 52 个不同硬件组合。

截图已检查主副屏桌面、搜索、设置、全屏、跨屏后文件夹，未见比例错乱、文本裁切或残留覆盖层。桌面捕获可能含原有输入法浮动工具条；不把外部工具条当作应用绘制内容。

- 矩阵末尾 surface 恢复后直接调用 Pixi `hitTest` 遇到空事件根。补试先发正常 pointermove 初始化事件路径，再用实际 OS 点击设置，两屏均通过。原始矩阵仍保留失败记录，不伪装整次运行全部通过；独立恢复补试才是恢复输入的有效证据。

- 实验性 Live Desktop 桌面捕获未开启，不把普通系统材质/壁纸的结果扩展到该实验功能。
- 应用内拖拽跨屏使用产品真实拖拽会话与窗口迁移 API；OS 鼠标跨屏拖动窗口另有独立测试，不能将两者混为一谈。

本轮为硬件验收，未修改产品功能。4 个临时修改的文件已逐字恢复并核对 SHA256，包括原本有未提交修改的 nativeProduct；临时 audit 源文件归档后移除。显示器配置的测试前后枚举 SHA256 相同，`git diff --check` 通过。保留报告与本地证据，未提交或推送。

## 后续：同屏修改缩放导致全屏边界漂移

用户补充：屏幕 2 全屏，Windows 缩放由 150% 改为 125% 后窗口溢出到屏幕 1，跨屏重新打开才恢复。此场景没有包含在上述固定缩放的双向跨屏测试中。

代码确认的缺口：`native-app.ts` 收到 DPI/display 通知时只根据现有 HWND 更新渲染尺寸；`native-window-presentation.ts` 的同模式 `setMode` 直接返回，而快捷键定位只有显示器身份变化才重算物理边界。因此窗口接受 DPI 消息建议矩形后，缺少全屏几何校正；跨屏定位恰好重建边界。

修正：全屏窗口在同步 viewport/backing 之前，按当前显示器物理矩形和物理超扫重新贴合。相同边界不重复调用 SetWindowPos，使用无激活/无 Z-order 更改，并防止重入；最小化时不改矩形，恢复时再同步。重复设置同一全屏模式和同屏快捷键激活也检查边界。保存的窗口模式位置不被这些刷新覆盖，普通窗口继续遵循系统建议矩形。

验证：隔离窗口重放带偏移建议矩形的 `WM_DPICHANGED` 与 `WM_DISPLAYCHANGE`；两屏 × 超扫 0/1 × 两类消息共 8 例。修正前 8 例均不能恢复边界，修正后 8 例均恢复，HWND、客户区、GPU 子窗口与 backing 一致。原始证据 `artifacts/fullscreen-dpi-refresh/before/` 和 `after/`。永久回归 `nativeFullscreenBoundsSmoke.ts` 已接入完整 Native smoke，另验证退出全屏的原窗口位置和普通窗口 DPI 建议矩形。

重放不修改真实 Windows 缩放值。曾为用户准备 90 秒屏幕 2 全屏观察窗口，但未记录到实际缩放变化，`manual/proof.json` 为空；不能把它算作 150%→125% 原地切换实测。Windows 文档明确指出跨显示器和显示器自身 DPI 变化都会触发此消息：[WM_DPICHANGED](https://learn.microsoft.com/en-us/windows/win32/hidpi/wm-dpichanged)。本次结论是原生通知路径及边界修复已验证，实际系统缩放操作仍待用户验证。

全量测试、app/tools/native 类型检查、policy/i18n 与生产构建通过。最终完整 Native smoke exit 0（`artifacts/fullscreen-dpi-refresh/native-smoke.log`），包括新增 8 种全屏通知与普通窗口恢复检查、213 帧拖拽交接、文件夹长按/重开/分页/改名、隐藏恢复与持久化。重放前后截图已查看。临时诊断入口已归档清除，nativeProduct 恢复到本轮开始的逐字内容；保留正式修复与永久回归。本次未提交，工作区此前独立 SDK/CopySrc/stress 改动仍保留。
