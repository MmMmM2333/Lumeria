## 修复与同类排查结果

nativeMain 统一取消入口同时消费引擎输出、释放 pointer capture、清空 touchId、清理 deadline
和手势呈现。修复键盘操作、外部桌面页提交、launchFlow 三处丢弃 cancel 返回值的路径。
失焦、进入设置、应用离开 running 状态和输入解绑也走统一清理；启动交互阻塞期间收到
指针事件时，若仍持有手势则取消，避免终止事件被直接忽略。

正常输出的 releasesPointer 在执行命令前释放，避免激活同步触发隐藏或另一轮取消时仍看到
旧指针。滚轮被指针打断的入口原本会消费输出，保留其当前指针所有权判断。

新增原生回归覆盖：按住图标后 Ctrl+方向键翻页、失焦、进入设置、隐藏，以及迟到的抬起事件；
断言 touchId 和原生 capture 均已释放，并用实际原生输入确认后续文件夹可打开。
完整 native:smoke（PID10900，退出码0）通过，包含正常拖拽/取消、120帧拖拽呈现、触控板、
文件夹中断、显隐及最小化恢复；npm run check 和 git diff --check 通过。

## 已确认的同类故障

独立原生窗口中按以下顺序稳定产生“图标/文件夹不能激活，但能翻页”：
按住桌面图标 → Ctrl+右方向键切页 → 松开鼠标 → 点击文件夹 → 再用Ctrl+方向键翻页。
测试直接使用原生指针注入和应用键盘处理函数，没有伪造touchId值。结果：

| 阶段 | touchId | 页码 | 拖拽 | 打开文件夹 |
|---|---:|---:|---|---|
| 初始 | null | 0 | false | 无 |
| 图标按下 | 1 | 0 | false | 无 |
| 键盘翻页 | 1 | 1 | false | 无 |
| 鼠标松开 | 1 | 1 | false | 无 |
| 点击文件夹 | 1 | 1 | false | 无 |
| 再翻页 | 1 | 2 | false | 无 |

根因：手势引擎cancelAll/cancelPointer清除内部pointer并返回releasesPointer；nativeMain的
键盘、外部页切换和launchFlow.cancelInputGesture等路径直接dispatch(cancel)而忽略返回值。
native适配层touchId未清空，后续pointerDown被touchId!==null条件拒绝；迟来的pointerUp在
引擎内部已无pointer，因而不再产生releasesPointer。滚轮/键盘翻页路径不依赖touchId，故仍工作。
touch函数在launch交互阻塞时还会直接return，终止事件可能无法完成适配层清理；需统一审查。

这证明了一个与用户症状一致的实际缺陷，不证明用户上次一定执行了这套操作。当前安装版未
启用devtools，无法回溯当时手势状态。无纹理加载/显存耗尽证据，不应先关联到GPU预算。

建议修复：统一取消入口，将引擎输出、pointer capture释放、touchId、deadline和press呈现
清理一起处理；显隐、失焦、设备恢复、键盘/外部页切换都调用该入口。不能仅在每次点击时
强制清touchId，那会破坏正常拖拽/多指所有权。补真实复现前后对照及正常点击/拖拽/取消回归。
以上为最初分析时的建议，后续实施结果见本文修复小节。

证据`.codex-dev/click-lock-analysis/{build.ts,result.json,run.log}`，测试PID16052正常退出。
用户实例PID18516保持运行。此症状既有完整smoke未覆盖“按住图标同时键盘取消”交叉序列，
因此此前回归通过不能排除此缺陷。

## 当前内存与改写 Rust 的边界

当前正常安装版PID18516只读采样：总工作集407.81MiB，私有工作集296.83MiB，私有提交
953.30MiB，峰值工作集688.50MiB。统计时间不同于用户看到的最低350MB，且未确认任务管理器
对应列，不能将两者直接作差。工作集不等于JS堆，提交不等于物理RAM。

模块映像驻留：bun.exe约22.49MiB，Skia约5.09MiB，Dawn约3.82MiB，NVIDIA主驱动约11.03MiB，
私有可执行页约6.86MiB；最大类别是私有数据约285.5MiB。DLL文件大小不是RAM，私有数据还
包括运行时堆、Skia/驱动/原生分配器，不能直接归成JS对象。

现有新策略190图标隔离样本，JSC堆44–61MiB（包含external24–28MiB），约20–33MiB是
heapSize减extraMemorySize的粗略JS对象部分；这不是完整当前用户进程的堆快照，也不包含
全部运行时映像/主线程Worker各自成本。图标编码约5.45MiB、GPU逻辑预算约57MiB；这些
数据在Rust中仍需要存储。以前ETW的Bun路径140MiB是提交/分配归类，不是可直接节省的RAM。

| 改写范围 | 可能减少 | 仍然存在 |
|---|---|---|
| 业务逻辑改Rust，仍保留Pixi/JS UI | 部分状态对象、计算/序列化开销 | Bun/JSC、Pixi场景、Skia与GPU栈大部分保留；跨语言副本可能增加 |
| UI/场景也重写Rust，真正移除Bun/JSC/Pixi | JIT/运行时、JS对象及部分场景元数据/GC高水位 | Rust侧场景/布局/事件/文字数据、图片解码、GPU纹理、D3D/驱动仍存在 |
| 同时更换渲染/文字/窗口架构 | 可以重新设计资源池、缓冲、字体和依赖 | 属于架构收益，不能仅归因Rust语言；需要同功能实测 |

结论：全量原生Rust实现有机会降低内存，但无法承诺350MB→某个固定数字或去掉大部分占用。
保持Skia与D3D/WebGPU相同的情况下，不会自动消除原生分配池和驱动成本。纯业务迁移收益
较受限，不建议为此先全面重写。先修点击状态缺陷，再测模块/设置惰性初始化、节点预建控件、
解码临时资源/池保留；如考虑Rust，做同窗口/DPI/190图标/文字/透明/输入法/动画的最小
等价原型，比较整组私有驻留、提交、峰值和交互，再决定迁移范围。
