# Native 其他堆增长入口：实测记录

日期：2026-09-12。主体保留基于渲染更新分离后的测量数据；测量阶段没有修改产品运行代码。用户随后授权的状态投影与退出调度修复，记录于末节。工作区尚未提交，已有壁纸与渲染更新改动保留。

## 测量口径

- 每个场景使用独立进程、临时数据目录，顺序执行，未操作用户安装版的数据。
- 常规组：190 个应用、63 个顶层条目、3 个桌面页和 36 个文件夹。小文件夹 4 项，大文件夹 23 项分成 2 页。图标为 256×256 PNG；窗口基线 900×600。
- 压力组：1,000 个应用平铺于 48 页，复用 190 张图标。与常规组的文件夹拓扑不同，只作压力参考，不作纯数量的线性缩放实验。
- 每场景 6 轮。搜索/筛选 66 次查询变化；多选 30 次选中加 6 次清除；持久化开关 12 次；设置路由切换 18 次；文件夹开关或翻页各 6 次；拖拽 6 次、72 个移动样本并取消；resize 36 次；模糊滑块 72 次；改名保存 30 次。
- 先预热、记录初始桌面，再进入待测页面并记录 ready 基线。操作完成后清理 UI、静置 10 秒，最后单独执行诊断 GC。截图在所有采样结束之后，避免截图缓冲污染峰值。
- 约每 100ms 记录 JSC 统计及节点数；独立 Python 进程记录 Windows 私有工作集、私有提交量。同步重操作后也立即采样。表中是观测峰值，不是瞬时峰值的严格上界。
- 准备阶段已打开的列表、文件夹或背景预览算入 ready 基线；“首次打开成本”另列，不能与后续调整成本混淆。

### Bun 指标的重要区别

根据 [Bun HeapStats 定义](https://bun.sh/reference/bun/jsc/HeapStats)，`heapSize` 与 `heapCapacity` 都包含 `extraMemorySize`；后者包括字符串内容、ArrayBuffer 等在对象区外分配的内存。这里逐样本计算：

`对象区容量 = heapCapacity - extraMemorySize`

对象区容量是预留容量，不等于存活对象大小。`heapSize`、`objectCount` 反映最近一次 GC 的存活统计，不能当成每一刻的全部临时分配量。诊断 GC 后再观察存活量更有意义。

各列峰值可能出现在不同采样时刻，且 JSC 统计与 OS 驻留口径不同，不能相加；JSC 数值也不等于独立显存占用。

## 已定位的重复工作入口

1. **设置面板整体重建。** 66 次列表查询产生 69 次 redraw（含准备阶段），30 次选中加 6 次清除产生 39 次 redraw。操作期间可见树节点数量保持 2,188，但重建累计耗时分别约 1,153ms 和 741ms。净节点数稳定不等于没有创建/销毁压力。
2. **状态映射每次读取产生新引用。** `stateHost.ts` 的 native `derived` getter 每次执行计算；`launchpadApps.ts` 的 `launchTargetStatusById` 使用 `Object.fromEntries`，即使内容不变也产生新对象。`nativeMain` 的诊断快照按字段引用判断变化，因此会使快照及场景依赖比较失效。实测列表筛选过程累计约 71 次桌面 structure 更新，与本不需要改变桌面内容的 UI 通知同时发生。代码链说明该路径会造成无效更新；其独立内存贡献仍需单因素对照。
3. **空查询也构建桌面搜索文档。** `changeSearch` 在决定是否真正搜索之前构建文档。持久化、改名保存会连带调用它。
4. **资源遍历不是这轮最主要耗时。** 改名保存触发 31 次图标收集；拖拽复测 5 次收集累计约 0.31ms。纯翻页、文件夹翻页及设置筛选均没有触发资源所有权收集。表中改名保存的 +61 MiB 属于整个保存/布局/搜索链，不能全部归到 `retainLayout`。
5. **文字重建主要体现在外部缓冲。** 实际 2×/3× 切换时对象区容量仅增约 2.8 MiB，而 JSC 外部统计增约 54.9 MiB；进程驻留增量又只有约 11.4 MiB。再次说明这些口径不能混加或一概归为节点对象。

建议后续顺序：先稳定未变化状态映射的引用、避免无关通知重建桌面；再减少列表/设置的整页 redraw 并追踪 GC 后持有；另开图片加载对照优化 4K 双预览；最后处理文件夹开关与拖拽中的剩余计划/投影分配。不先调整 Dawn 的全局分配策略。

## 有效性、异常与未做事项

- 有效操作采样时段均没有 renderer recovery 或 uncaught exception。文档主表只使用有完整 6 轮数据的结果。
- 单项和批量拖拽样本在采样完成、截图及退出之后，重复出现 `NativeDesktopScene has been destroyed` 回调异常。额外清理和复测后仍能出现。数字来自异常之前的完整操作时段；这是独立的退出生命周期问题，不能因为进程返回 0 就称作“退出正常”。本轮没有修改产品代码修复它。
- 最初无实际密度变化的文字测试在采样后截图时触发一次恢复，未进入最终文字重建表；最终 2×/3× 数据没有该事件。
- 截图仅用于确认场景。列表、文件夹截图已查看；背景截图处于设置滚动区域上方，预览加载通过真实 view ready/error 状态及滑块操作验证，未将截图缓冲纳入测量。
- 没有进行 GPU 专用显存/完整 native 堆分配栈追踪，也没有进行真实多显示器 DPI 切换。没有把差额全部认定为 JS 对象或泄漏。
- 本轮未运行产品修复测试，也未提交代码，因为没有更改产品运行逻辑。所有测量实例已退出，安装版未替换。

## 后续修复：稳定状态投影与退出调度

用户授权先完成稳定派生状态引用，并修复拖拽后退出异常；此次不改变设置列表整页 redraw 方式。

### 实现

- `launchpadApps.ts` 按目标检查记录的源引用缓存状态映射；源记录替换后，如果 id/status 内容仍相同，继续复用旧映射。真实状态改变或清除时才生成新映射，发布结果冻结，避免调用方修改共享缓存。没有给全部 native derived getter 增加不完整的通用缓存。
- 新增 `nativeSceneScheduler.ts` 统一管理待执行任务及 renderer 连接。每个排队任务有独立身份；同步提交会使旧任务失效；提交中产生的新请求不丢失；启动阶段的请求等待 renderer 连接。
- 退出开始即断开 renderer 并取消任务，然后才处理窗口效果、托盘及拖拽等清理。替换了 nativeMain 的分散布尔队列标记；延迟的目标检查结果也遵循同一个 disposed 状态。真正运行中的渲染错误仍会向外抛出。

退出调查中，加时序日志的一次运行没有复现异常，但确认任务会在场景销毁后被唤醒。修复没有据此推断 JIT 或驱动故障，而是在调度生命周期边界上取消过期工作，并以不含时序日志的运行复测。

## 后续修复：应用管理页局部更新与绘图上下文释放

### 持有关系

对同一筛选场景获取了操作前、关闭页面并 GC 后的配对堆快照。强引用路径为：

`WebGPURenderer → graphicsContext._managedContexts.items → GraphicsContext → _gpuData → GpuGraphicsContext`

安装的 Pixi 8.20.1 中，`Graphics.destroy({ children: true })` 不会像无参数 `destroy()` 那样自动销毁默认拥有的 context。原页面递归销毁使用前者，导致已移除页面的绘图上下文仍被渲染器资源表持有；JS GC 本身不能断开这条引用。

新增 `nativeGraphicsLifecycle.ts`，在页面、过渡页、虚拟行、滚动容器和分离的页脚控件退出前，通过公开的 `Graphics.context.unload()` 释放渲染器引用，再执行原有组件销毁。这里没有销毁共享 context 的 CPU 内容，也没有清空全局缓存或依赖私有 `_ownedContext` 字段。

同一筛选测试的 GC 快照对象数量增量：

| 类型 | 修复前 | 修复后 |
|---|---:|---:|
| GraphicsContext | +6,761 | 0 |
| GpuGraphicsContext | +6,761 | 0 |
| GraphicsPath | +11,395 | 0 |
| CanvasTextMetrics | +952 | +326 |

剩余文字测量对象的持有路径是 Pixi 的 `lru(1000)` 缓存，保留其原有策略，不把有界缓存当作页面泄漏强行清空。

### 局部更新

- 应用管理页保留搜索框、计数、操作栏、滚动容器和虚拟列表；筛选只变更列表数据和必要行。
- 虚拟行按稳定 ID 复用，顺序变化更新位置；名称、目标或图标内容变化时仅重建该行。行点击读取当前选择状态，不依赖上次绘制时的选中值。
- 多选只更新已挂载行的勾选/高亮、计数、操作按钮和选择工具条的展开状态。
- 键盘焦点按稳定 key 关联，修正复用后旧索引和重复 focus 监听的问题；保留输入光标、滚动位置及空结果交互。
- `NativeSettingsShell.refreshContent()` 在相同路由/主题且页面支持更新时执行局部刷新。路由、主题、尺寸等真正变化仍走重建。
- 本轮局部更新范围是应用管理页。排除列表及其他设置页仍保留原更新方式，但共享资源释放边界已修正。
