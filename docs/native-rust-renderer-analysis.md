# 假设 PixiRust：能改善多少内存

这是基于当前测量的架构分析，不是在推荐一个已验证的 Pixi Rust 移植库，也没有启动 Rust 重写。

## 当前证据支持的结论

冷启动完整桌面的私有驻留页扫描约 250 MiB，其中 Bun/JSC 分配路径约 133 MiB，图形内核、驱动和 Dawn 约 72 MiB。Bun/JSC 是最大的单项，覆盖 Pixi、应用逻辑以及引擎解析、字节码、JIT、GC 等成本，不能全部归给 Pixi 单库。

这也不是对历史接近 400 MiB 状态的完整解释。设备恢复后的额外占用还存在独立的原生资源问题，不能因换语言就假定消失。

## 迁移范围决定收益

| 假设方案 | 可以减少的部分 | 仍然保留的部分 |
|---|---|---|
| Pixi 核心变成 Rust 库，由现有 JS 调用 | 一部分 Pixi 解析/JIT、节点和渲染计算开销 | Bun/JSC、JS 应用与设置代码、JS 包装对象、跨语言接口 |
| Rust 持有场景树、布局、动画与批处理，JS 只传批量状态变更 | 更多节点和每帧执行开销；可减少频繁 JS 分配 | JS 运行时和业务代码；需要处理跨边界资源所有权 |
| 界面与应用逻辑也原生化，移除 Bun/JSC | 运行时解析/JIT/GC 管理等大量引擎成本，可采用紧凑的数据表示 | Rust 应用自己的数据、机器码、字体、图片、GPU/驱动、窗口与输入法 |

完整原生化具有更大的改善潜力。Rust 的所有权管理不要求 GC，常规原生编译也不需要在应用运行时 JIT 编译 Rust 代码；但分配器、线程、缓存和程序数据仍有成本。[Rust 官方说明](https://rust-lang.org/)

如果只是做逐节点 JS→Rust 包装，双方都持有完整场景树、每帧大量 setter 调用或频繁复制字符串/数组，收益会被抵消。更有价值的边界通常是：Rust 持有渲染状态和资源，JS 传递少量批量变更，避免重复数据模型。

## 为何不能承诺净省 133 MiB

1. 133 MiB 中包含当前应用需要的数据。迁移后仍要在 Rust 中存储布局、文字、图标描述、搜索数据等，只是表示方式改变。
2. 当前除 Bun/JSC 之外的部分合计已约 117 MiB。这只是“其余栈保持不变”的算术参考，不是 Rust 应用的理论下限或预计占用；更换窗口、字体或 GPU 后端也可能改变这些部分。
3. Rust 机器码和静态数据会占映像/文件映射页。私有工作集下降不必然等于同等幅度的总物理内存下降，应同时看总工作集与整个应用进程树。
4. `Box`、引用计数、哈希表、缓存以及 GPU 延迟释放仍可能保留内存。Rust 能更明确地表达所有权，但需要正确设计资源生命周期。
5. 若 PixiRust 同时从 Dawn 换成 wgpu 等后端，测量结果也包含后端策略变化，不能全部算成语言收益。

## 值得做的验证

先实现一个有限、同功能的对照原型：相同窗口尺寸/DPI、同一显卡、相同图标数量与分辨率、文件夹预览、文字、透明效果、翻页和输入法。分别记录空窗口、资源加载完成、操作后静置、设备恢复后的占用，以及帧时间。

测量整个进程树的私有工作集、总工作集、提交量和 GPU 内存；不要直接拿简单图形 demo 与完整启动台比较。采用紧凑节点存储、共享纹理和明确的资源句柄，才能判断收益来自何处。

现阶段结论：PixiRust 有改善机会；保留完整 JS 应用时收益范围有限且需要验证，移除 JS 运行时后潜力更大。当前证据不支持预报一个具体最终内存值，也不足以决定立即重写整个 Pixi。
