# 原生图标上传后的 CPU 像素释放

2026-09-09；产品基线 `86ad303`，Starter `0.3.2` / `b3d9206`，PixiJS `8.20.1`。

## 行为与边界

文件图标和 data URL 图标在 GPU 上传成功后释放解码后的 RGBA，保留加载时的编码图片快照。
GPU 纹理及 mipmap 沿用现有策略；未上传的图标仍保留 RGBA。原文件删除或覆盖不会改变
已经加载的图片，显式替换图标继续走仓库的替换流程。压缩恢复数据计入 CPU 内存，不能
把“RGBA 为零”表述成“图标完全不占内存”。data URL 的编码字符串按每字符 2 字节保守统计。

`NativeRecoverableIconSource` 使用 Pixi 的 WebGPU 上传扩展，在 `writeTexture` 返回后
释放像素引用。构造参数不保存 RGBA，避免 `TextureSource.options.resource` 继续持有原缓冲区。
专用扩展在 renderer 创建前注册，不改变其他纹理上传器。

Starter 的 `beforeRender` 在动画更新后、提交帧前检查资源；恢复期间保留上一帧并暂停动画推进。
图标准备遍历当前场景（含隐藏后代），对缺失 GPU 数据且已释放像素的来源以最多 4 路异步解码。
未挂入场景的纹理在再次使用时准备。Pixi 自动 GPU GC 不一定发出 source change，因此恢复前
调用标准 `unload()` 通知纹理与批次绑定失效。GPU 数据检测依赖锁定的 Pixi 8.20.1 内部结构，
升级 Pixi 时必须重跑该恢复测试。直接截图入口同样先准备资源。

设备恢复会替换原生输入对象；搜索栏通过已有 `rebindNativeInput` 接口重新绑定，应用的焦点
监听也重新订阅，避免图像恢复后键盘和焦点行为失效。销毁时清除编码快照，异步恢复不会复活
已销毁资源。首次加载失败仍由既有仓库处理；恢复失败明确进入错误路径，不呈现伪成功空图。

## 测量方法

复用 `docs/native-icon-stress.md` 的本机真实图标 fixture：200/1000 个独立文件、独立纹理，
尺寸和 mipmap 不变，900×600 窗口、每页 21 项。候选与基线使用同一 Starter 0.3.2、相同
诊断包和加载并发 4；基线仅从 `86ad303` 读取原加载器/仓库。逐页浏览后闲置 8 秒，再读取
Windows 工作集；另记录主动 GC 后的 JS 外部内存。各档基线 1 组，200 候选 1 组，1000
候选有 2 组内存样本。它们用于这台机器的对照，不代表跨机器统计结论。

| 指标 | 200 基线 | 200 候选 | 1000 基线 | 1000 候选（首组） |
|---|---:|---:|---:|---:|
| 全页闲置工作集 MiB | 445.27 | 396.42 | 728.86 | 552.77 |
| 私有工作集 MiB | 332.38 | 283.60 | 617.30 | 439.77 |
| 私有提交 MiB | 970.27 | 904.92 | 1739.21 | 1579.44 |
| 图标 CPU RGBA MiB | 45.07 | 0 | 224.71 | 0 |
| 编码恢复数据 MiB | 0 | 5.62 | 0 | 28.71 |
| GC 后 JS 外部内存 MiB | 58.68 | 19.39 | 239.86 | 43.61 |
| 图标加载耗时 ms | 77.25 | 76.93 | 320.34 | 321.73 |
| 加载期最长 10ms 定时器间隔 ms | 17.97 | 12.93 | 15.18 | 15.55 |
| 全程峰值工作集 MiB | 545.71 | 532.78 | 1150.67 | 1143.06 |
| 12 次键盘输入至呈现中位数 ms | 29.24 | 31.03 | 45.16 | 44.28 |

200 图标直接保留的图片数据净减少约 39.45 MiB，1000 图标约 196.00 MiB。
首组 Windows 闲置工作集分别减少 48.85 / 176.09 MiB。进程工作集受分配器、驱动和系统回收
影响，不与图片字节数一一相等。1000 候选第二组闲置工作集 521.45 MiB、全程峰值
1088.92 MiB、加载 335.02 ms；其后窗口被最小化，输入阶段中断，仅保留已完成的内存数据，
不把该组当作交互/恢复通过证据。

收益随已上传的图标数量增加。1000 图标首屏仅 42 个纹理上传时，候选仍保留 214.42 MiB
RGBA 和 28.71 MiB 编码数据，合计反而高于基线 224.71 MiB；因此这一步改善的是上传后的
长期驻留，不能宣称首屏、全程峰值或全量加载策略都已优化。全程峰值首组差异很小，未证明
稳定下降。冷图标预算缓存和首屏优先加载不在本轮范围。

## 验证与证据

- `npm run check` 通过：现有测试、新恢复单测、应用/工具/原生类型检查、策略、i18n、构建。
  既有大 chunk 提示仍在。新增 native smoke 明确由 `tsconfig.electrobun.json` 检查；浏览器
  配置沿用原生测试边界，不让 Bun/Electrobun 实现被浏览器配置重复编译。
- `npm run native:smoke` 最终通过，PID 32924 正常退出。真实 GPU 测试直接读回纹理，验证
  首次上传、显式 unload、GPU GC、device-lost 后与解码输入逐字节相等，且每次重传后 RGBA
  再次归零。后续完整交互覆盖恢复后的搜索/IME/Escape、文件夹、拖拽、设置、输入和窗口。
- 单测覆盖上传失败保留像素、构造参数不残留像素引用、原文件覆盖/删除后恢复、data URL、
  损坏恢复来源明确失败、恢复去重，以及解码期间销毁。
- 压力测试全部独立纹理数正确、pending/failed 为零，逐页浏览后全部上传。首组200/1000
  均完成强制 GC、12 次键盘输入和设备恢复；已查看恢复后的真实图标截图。
- 1000 图标短恢复测试：device-lost 注入到新 generation 的首个成功 presented 为
  290.74 ms（另一短样本 295.46 ms）。随后从第1页跳至第48页再返回，等待 motion.active=false，
  轨道位置精确到 -42300/0，应用保持 running、无错误，最终截图正常。该时间包括 runtime
  重建与资源准备，不等同于纯图片解码耗时。证据在 `run-1000-release-recovery-settled`。
  只访问部分页面的恢复测试仍有尚未上传的 RGBA，因此不要求它的全仓库 CPU 像素为零。
- Starter 上游类型检查、4 项准备入口测试（17 断言）、既有 host 测试及独立 consumer smoke
  通过；正式制品 560 文件校验通过。消费者未私改 vendor，升级临时旧 vendor 备份已清理。

原始证据位于 `.codex-dev/icon-stress/run-{200,1000}-release-{base1,candidate2}`；第二组
内存样本为 `run-1000-release-candidate3`。候选1仍有构造参数像素引用，已作废，不用于结论。
汇总为 `.codex-dev/icon-release-results.json`，方法脚本为 `build-icon-load.ts`、
`run-icon-release.ps1`、`summarize-icon-release.py`。最终检查和原生验证日志分别为
`.codex-dev/icon-release-check.log`、`.codex-dev/icon-release-native-smoke-final.log`。
