## 结论与优先级

1. **优先修搜索结果切换与退出搜索**：桌面节点缓存会随查询结果数量收缩；搜索又会一次实现多页结果，导致集中创建/销毁图标。真实 Native 测量确认存在百毫秒级同步场景开销。
2. **再优化勾选和键盘焦点**：已避免重设所有图标，但这两类变化仍触发完整布局计划；只变一个勾选或两个焦点图标，也要扫描整个保留桌面。
3. **搜索匹配算法是次要但可见的开销**：拉丁字母查询对未匹配的中文名称执行多音字兜底。不要通过关闭中文匹配功能来掩盖它。
4. **普通翻页优先级较低**：专用翻页路径已避免全量结构重建；800 个独立图标的长距离跳页仍有少量长帧，需要进一步区分图标准备、CPU 遍历与 GPU 绘制。
5. **全量 app 类型检查只有两个根因、六条报错**：两处最小类型修正的临时实验可让 app/tools/native 全部通过，无需关闭严格检查。

## 测量方法与边界

- 复用真实 Native `--smoke --search --settings-only` 路径，用独立生成的 256px 图标，全部纹理准备后测量。搜索夹具分别配置 300/600 个应用，初始化后额外存在一个测试应用，实际桌面数量为 301/601。
- 每组进行 3 轮 `w → wo → wor → word → Word 0 → zzzz → yingyong → 应用 → 清空`，另测 12 次焦点移动、12 次勾选。300 组补跑一次节点创建/销毁计数。
- 记录同步输入调用、真实 `scene.commit`、完整计划数、`IconNode.setState` 次数、到下一次 `presented` 事件的时间。使用查询接口/原生输入路由，不代表物理键盘到显示器扫描出的延迟。
- 性能探针有开销；记录到下一次呈现为止，延迟销毁可能归入下一条样本。3 次查询不适合泛化为稳定 P95，因此下表报告范围。Node 独立 CPU 实验与 Native/Bun 数字不可直接相减。
- Native 搜索验证 3 次均通过，包括搜索启动、清空、重新显示、设置遮挡与改名后的索引失效。已有输入/退格基准确认新增纹理源为 0，瓶颈不能简单归结为反复解码图标。
- 本轮没有 GPU timestamp 分段测量、冷磁盘首搜测量、真实用户目录采集；不宣称覆盖所有硬件和布局。

## 真实 Native 结果

| 场景 | 300 应用 | 600 应用 | 工作量 |
| --- | --- | --- | --- |
| 清空搜索回桌面，scene CPU | 133–176 ms | 299–498 ms | 301/601 次 setState；通常 1 次完整计划 |
| 空结果切到 `yingyong`，scene CPU | 90–129 ms | 197–287 ms | 200/400 次 setState；偶尔另有一次结构通知 |
| 结果不变的 `w → wo`，scene CPU | 2.9–4.8 ms | 5.7–6.2 ms | 仍做 1 次完整计划，0 次 setState |
| 逐个勾选，scene CPU | 7.2–13.1 ms | 12.9–23.1 ms | 每次 1 次完整计划，1 次 setState |
| 搜索结果键盘焦点移动，scene CPU | 中位数 3.3 ms | 中位数 5.4 ms | 每次 1 次完整计划，2 次 setState |

勾选到下一次呈现的中位数分别为 21.0/35.3 ms；不应把全部剩余时间都算作布局开销。选择工具栏及其已有背景合成路径仍参与呈现，GPU 归因尚未确认。

### 搜索缓存问题的完整路径

- `nativeProduct.ts:744` 的 `changeSearch` 每次查询重新生成分页、快照、投影 epoch，并同步 `renderScene`。即使 `w/wo/word` 的结果与顺序完全相同，仍会做完整计划。
- `desktopRenderPlan.ts:625` 的节点 key 包含 `search/page + pageIndex + appId`。桌面与搜索分别使用节点；搜索结果重新分页也可能改变 key。
- `NativeDesktopScene.ts:256` 在不少于 4 页且不超过 800 个条目时保留全部页面，搜索结果同样适用。因此首次搜索可能一次创建 100/200 个节点，切换中文组再创建 200/400 个。
- `DesktopLayer.ts:1724` 只在桌面/搜索 scope 切换时把普通 app 放入搜索缓存；同一搜索内不再匹配的节点通常进入退场/销毁路径。
- `DesktopLayer.ts:1748` 以最近两次计划的条目数决定缓存上限。进入搜索时可以暂存全部桌面节点，但第二个字符后的两份计划都只含搜索结果，桌面缓存开始被淘汰；查询收窄和空结果会进一步缩小上限。

补跑计数证实：300 夹具第一次 `w` 创建 100 个搜索节点；`wo` 结果不变，却观察到 201 个缓存节点销毁；切到 `yingyong` 创建 200 个；清空搜索时又创建 300 个桌面节点。延迟销毁的具体执行时点可能在下一次样本，但完整链路与缓存实现一致。

建议：桌面保留集合与搜索结果缓存分别管理，在既有资源预算内使用稳定容量；搜索只实现当前页与邻页；同一查询结果 ID、顺序和相关版本未变时跳过布局投影。不要简单取消缓存上限或无界保留每个历史查询，也不要为躲开卡顿直接延迟所有输入。

### 勾选与焦点

`NativeDesktopScene.ts:371` 把 `selectedAppIds`、`focusedIcon` 纳入结构依赖。之前的 `canRetainAppVisualState` 已将实际视觉更新缩到 1–2 个节点，但不能避免完整布局计划、边界登记和遍历。

建议为选择/焦点增加局部更新路径，明确维护旧/新焦点、选中差集与必要的预览状态；仅当布局、拖拽或文件夹交接同时变化时回到结构路径。应验证 Shift 范围选择、跨页选择、搜索焦点和取消选择，不能只优化单次点击。

### 搜索匹配 CPU

`launchpadSearch.ts:368` 对未被普通字段命中的中文名字调用 `pinyin-pro match`，支持多音字。已有拼音字段缓存不覆盖这一步。

混合英文/中文名称独立 Node 测量（每查询 80 次）：

| 查询 | 300 应用 P50 | 600 应用 P50 | 900 应用 P50 |
| --- | --- | --- | --- |
| `w` | 0.04 ms | 0.06 ms | 0.07 ms |
| `wo` / `word` / `zzzz` | 2.6 ms | 5.2–5.4 ms | 7.9–8.4 ms |
| `yingyong` / `应用` | 0.03–0.06 ms | 0.05–0.10 ms | 0.08–0.15 ms |

索引构建在这些样本中约 6–12 ms。Native 当前在首次非空查询时建索引；布局页引用变化会失效，即使只是移动图标。这是后续优化候选：按 app 名称/搜索内容版本保留文档，保留原始排序语义；对兜底匹配做有界缓存或预计算可复用信息，并保留多音字回归测试。算法次要于当前百毫秒级节点创建。

## 其他场景

### 翻页

使用已有 800 个独立 128px 图标、10×80 网格的隔离基准，0 与 9 页之间跳转：

- 正常路径 4 次：同步提交 12.5–19.4 ms，完整结构重建 0 次；动画帧间隔 P95 17.1–18.6 ms，最大 24.9–39.6 ms，每次 6–9 帧超过 16.67 ms。
- 基准的强制失效对照同步提交 29.2–33.7 ms，各有 1 次结构重建；它不是旧版本性能对照，且总是在正常组前运行。
- `updateRetainedPage` 仍重设来源页与目标页节点（本夹具最多 160 个），`cullRetainedPages` 每帧遍历保留图标；`nativeIconResidency.prepareFrame` 还有可见树遍历及资源整理。静态路径存在优化空间，但本轮未证明这些各占多少 CPU/GPU 时间。

### 连续调整窗口大小与常驻规模

不含 GPU 呈现的 Node 场景实验：连续 resize 的 scene CPU P95，300/600 应用分别约 11.1/17.2 ms。超过保留阈值的 900 应用组反而约 4.8 ms，因为只实现可见邻页。这说明开销取决于实现的节点数量，而不只取决于总应用数；不能据此说 900 应用整体体验一定更好，翻页时还需重新实现节点。

窗口 resize、图标尺寸/网格改变需要新几何，不能直接跳过计划。建议评估按可见页即时更新、其余保留页延后更新，并保证 resize 后命中边界准确。

### 尚未测实的候选

- 高 DPI、大壁纸、模糊强度连续拖动：`nativeBackgroundSettings.ts:55/86` 会刷新预览并配置背景处理，可能形成重复离屏绘制；本轮没有 GPU 证据，不能认定为已复现瓶颈。
- 设置内应用管理搜索使用虚拟列表，且有 `updateVisible` 更新路径，不能套用桌面搜索节点缓存的结论；本轮仅检查实现，未单独跑其大量输入基准。
- 首次打开大文件夹、GPU 恢复和冷图标载入仍应独立测量。本轮没有重复声称上一轮的创建动画结果适用于这些场景。

## 全量 app 类型错误

当前 `npm run typecheck:app` 共 6 条诊断，全部发生在前次性能提交未修改的两个文件：

1. **背景 recipe：2 条，同一根因。** `NativeBackground.ts:17` 声明 `context?: WindowsImagePlacementContext`；`configure` 的可选参数可能为 `undefined`，但第 74 行始终创建含 `context` 属性的对象。app 配置启用 `exactOptionalPropertyTypes`，此时“可省略属性”不等于“允许显式 undefined”。赋给字段与传给方法分别报 TS2375/TS2379。引入于 `bb15900`。运行时现有逻辑允许没有 context，未由此证明运行时崩溃。
2. **视觉测试：4 条，同一根因。** `nativeVisualParity.test.ts:29/31/41/43` 将视觉子状态传给 `applyFolderOverlayAlpha`，而该方法声明接受完整 `DesktopLayerState | DesktopVisualFrame`，要求大量几何字段。实现实际只读取 `launchpadVisualAlpha`，因此是签名依赖过宽与测试调用的契约不一致；并非真的需要为透明度测试补上几十个布局字段。引入测试的提交为 `7c5b5b1`。

为什么 Native 类型检查此前通过：Native 配置继承 SDK consumer 配置，没有启用 `exactOptionalPropertyTypes`；它通过产品依赖检查了 `NativeBackground.ts`，但没有纳入 `nativeVisualParity.test.ts`。app 配置的范围更广，包含这份测试，且可选属性检查更严格。名称为 app 的检查并不只检查旧 Vue UI。

最小修正实验：将内部 recipe 明确声明为 `context: WindowsImagePlacementContext | undefined`；将透明度方法参数收窄为 `Pick<DesktopVisualFrame, "launchpadVisualAlpha">`。**完整 `npm run typecheck`（app/tools/native）通过。** 没有添加 any、类型断言或关闭严格检查。实验后恢复源文件，因此当前工作区的 6 条报错仍存在，等待实施修正。
