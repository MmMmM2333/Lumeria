# Native 构建方式与诊断裁剪：对照结果

日期：2026-09-12。承接 [原生分配调用栈分析](native-allocation-stack-analysis.md)，验证用户确认的第 1、2 项：ESM / CJS / bytecode / minify，以及剥离 smoke、截图和 benchmark 代码的收益。

## 结论

- **没有证据支持为降低内存而切换到 CJS、bytecode 或 minify。** 同一 Bun 构建管线下，普通 ESM 静止约 239 MiB，bytecode 约 240–243 MiB，bytecode + minify 约 239–240 MiB。bytecode 缓存已经实际命中。
- **诊断裁剪有小幅、可重复的收益。** ESM 产物减少约 272 KB（5.7%）；静止私有工作集约从 239 降至 230–234 MiB，交互后诊断 GC 的数值约从 268 降至 261 MiB。JSC 存活统计减少约 3 MiB。它不能解决整体 400 MiB 问题。
- 15 次有效独立进程试验均通过设置、文件夹、翻页检查；11 张结束后的桌面截图逐像素一致。没有更改默认构建或产品源码，也没有把实验 AST 裁剪器接入正式构建。

## 方法与控制

所有格式对照使用包内 **Bun 1.4.2** 构建并运行。同一份实际布局：195 个应用、36 个文件夹、3 个桌面页；每次复制到独立临时目录。保留默认 GPU、透明、MSAA、900×600、resolution=1、相同图标预加载策略。

首次试跑因窗口被最小化而终止，未纳入数据。后续所有实例将窗口放到屏幕外，保持 running、未最小化并持续按需渲染，避免干扰用户工作。因而本轮是 CPU 渲染及场景内容对照，**不是显示器端到端呈现延迟测试**。

每个实例依次：

1. 首屏与入场动画完成，等待图标预加载清空。
2. 静置约 8 秒、再静置 20 秒，分别记录两次静止值；原始数据的标签为 `idle-10` / `idle-30`，实际按上述定时执行。
3. 8 次桌面翻页并回到原页；首次打开/关闭设置；打开/关闭文件夹。
4. 等待约 10 秒记录自然回落，再执行一次诊断 GC、等待 1.2 秒记录。
5. 后 11 个实例在全部内存采样结束后提取桌面 PNG。截图缓冲不计入启动峰值和表中的采样值。

独立父进程约每 50ms 读取 `GetProcessMemoryInfo` 的私有工作集；通过进程名及完整 exe 路径匹配自己创建的实例。启动峰值是观察到的采样峰值，不是严格上界。每轮是新进程，Windows 文件缓存保持正常，并未人为清空磁盘缓存。

常规探针在 devtools 服务启动前进入测量，因此这里隔离的是诊断代码的加载/编译成本，没有把“实际开启与关闭 devtools HTTP 服务”混入对照。

## 同构建器下的格式比较

单位 MiB；列出两次实测范围，压缩 ESM 仅作一次补充对照。

| 构建 | 次数 | 启动私有工作集观测峰值 | 预热后静止约 28 秒 | 交互后诊断 GC |
|---|---:|---:|---:|---:|
| Bun ESM | 2 | 320.26–323.38 | 238.80–239.07 | 267.83–267.98 |
| Bun CJS，无 bytecode | 2 | 316.19–318.73 | 242.57–250.52 | 268.23–271.55 |
| CJS + bytecode | 2 | 329.10–330.96 | 239.96–243.42 | 274.54–275.57 |
| CJS + bytecode + minify | 2 | 324.58–325.83 | 239.44–240.06 | 272.17–279.77 |
| Bun ESM + minify | 1 | 312.00 | 242.95 | 267.46 |

bytecode 文件与运行时版本匹配，日志每次都出现了 app 入口缓存命中。它没有避免运行时 JIT、对象创建和所有代码/常量的驻留，不能简单把上一轮“解析 / 字节码路径的 31 MiB”当成可以全部删除的内存。

源码文件大小明显减少也未带来相同幅度的 RAM 收益：未压缩 CJS 源码约 4.85 MB，bytecode 约 9.05 MB；minify 后源码约 2.80 MB，bytecode 仍约 8.60 MB。这里 MB 为产物字节数的十进制近似值，与内存表的 MiB 区分。

普通 CJS 单列作为控制，避免把 ESM→CJS 的变化全部算给 bytecode。当前正式管线已经提供 `native:build:bytecode`，本次实验复用了其 Bun 版本、CJS、import.meta 替换及 banner 约束，没有新增第二套产品字节码实现。

## 诊断代码裁剪

本轮在实验构建插件中用 TypeScript AST 做可核对的裁剪：

- 去掉 nativeMain 中的 7 个 smoke / 像素 / 截图 / 原生点击辅助函数，以及 `nativeSettingsSmoke` 静态导入。
- 将 smoke 分支和诊断环境开关折叠为关闭状态，保留正常应用分支和错误处理。
- 移除 devtools 入口调用及其无用依赖。
- 去掉 touchpad capture、settings preview、restart smoke 和 memory benchmark 的诊断入口。
- 保留底层原生宿主自身的诊断/恢复支持，不把整个 SDK 的调试能力算作已删除。

已检查产物中不再出现 folder context smoke、activation smoke、原生截图辅助脚本、memory benchmark、像素 smoke 和 devtools 入口标记。生产功能路径仍由同一源码生成。

| 构建 | 预热后静止约 28 秒 MiB | 交互后自然静置 10 秒 MiB | 交互后诊断 GC MiB |
|---|---:|---:|---:|
| Bun ESM，保留诊断代码 | 238.80–239.07 | 300.23–302.07 | 267.83–267.98 |
| Bun ESM，裁去诊断代码 | 229.63–233.64 | 261.75–262.22 | 260.71–261.09 |
| bytecode + minify，保留诊断代码 | 239.44–240.06 | 273.14–301.96 | 272.17–279.77 |
| bytecode + minify，裁去诊断代码 | 237.78–240.15 | 267.21–267.36 | 266.47–269.59 |

自然回落时点受到 GC/分配器回收时机影响，不能把 ESM 自然静置列的约 40 MiB 差距都解释为“诊断代码永久占用”。强制 GC 后差距约 7 MiB，静止首屏差距约 5–9 MiB，才是更保守的收益表述。

ESM 的 JSC 静止存活统计约 47.1 MiB → 43.9–44.1 MiB，外部内存约 24.7 MiB → 21.7–21.9 MiB。对象区与外部内存的口径遵循之前报告，不能重复相加。

实验裁剪器按现有诊断结构匹配，适合验证收益；**不适合作为长期生产编译步骤直接接入**。若正式化，宜使用明确的测试入口/编译期能力边界，保留 dev 与 smoke 验证能力。实验阶段尚未做正式化；后续的编译期边界实现见文末。

## 当前实际开发产物的补充基线

既有 `native:dev` 产物与本轮 Bun.build 的 ESM 产物并不完全相同：原文件约 4.97 MB，开头为 createRequire 导入；Bun 对照包约 4.81 MB，含 @bun 标记。不能把两者当作唯一变量只有 bytecode 的对照。

为补齐实际基线，另复制当前开发产物，只增加相同测量逻辑和窗口位置调整，不重新打包其主体，运行两次：

| 当前开发产物 | 第 1 次 | 第 2 次 |
|---|---:|---:|
| 启动私有工作集峰值 MiB | 347.27 | 330.73 |
| 静止私有工作集 MiB | 262.15 | 240.84 |
| 交互后诊断 GC MiB | 290.59 | 274.61 |
| 父进程启动→首屏 ms | 2468 | 5953 |

波动明显，原因本轮未确定。它不支持声称“更换构建器必定省 20 多 MiB”，也不能凭其中一次较快启动认定速度收益。

Bun 同构建器格式组的父进程启动→首屏大多约 5.5–6.0 秒，bytecode 未显示明确量级改善。比较使用父进程启动时间，未把可能受模块初始化顺序影响的 `process-start` 日志当作唯一启动计时起点。

## 行为与渲染检查

15 个有效实例合计完成 120 次翻页、15 次设置打开/关闭和 15 次文件夹打开/关闭，全部正常退出。11 张最后桌面 PNG 均为 900×600，与裁剪 ESM 基准逐像素相同；已目视检查桌面布局、文件夹预览、文字和自绘标题栏。

采集的是 `renderer.render()` 的 CPU 耗时。各组 p95 约 2.26–2.85ms，p99 约 2.87–3.63ms。裁剪 ESM 的 p95 为 2.68–2.79ms，未裁剪 ESM 为 2.44–2.62ms；样本少、运行顺序和机器负载未完全随机化，不能证明性能完全等价，也不能据此断言稳定回退。此数据不等同于完整 JS 更新耗时、GPU 执行时间或显示器最终呈现帧时。

未切换正式构建、未替换安装包、未重启或对原开发实例执行 GC。原 PID 40484 保持运行。首次最小化导致失败的试跑单独保留并排除；15 个有效日志无 uncaught exception 且均有 shutdown 记录。

## 判断与下一步

1. 保持默认构建，暂不因内存理由切换 CJS / bytecode / minify。
2. 诊断代码从正式产物中剥离有收益，适合作为后续明确的生产/测试入口整理；预期是几 MiB 级收益，不是几十到上百 MiB 的整体解决方案。
3. 本轮没有推进用户暂未选择的设置页按需加载、smol、关闭 JIT 或其他架构调整。也没有把“项目里依赖存在”当成它们全部已加载的证据。

主要原始数据在忽略目录 `.codex-dev/build-study/results/`：各轮 JSON、50ms OS 采样、日志、PNG、`aggregate.json`。构建、运行、裁剪和探针分别为 `.codex-dev/build-study/build.ts`、`run.py`、`strip-diagnostics.ts`、`probe.ts`。同目录的 module-size-estimates 只估算发射代码体积，不换算成内存占比。

后续已采用显式编译期开关完成生产诊断排除，未接入实验 AST 名称匹配器。原生截图/点击辅助独立为诊断模块，dev/smoke 保留能力，生产 ESM 与可选 bytecode 都执行产物检查。默认模块格式和压缩策略没有切换；详情见 [生产诊断边界](native-diagnostics-build.md)。
