# Native 静止内存分析

日期：2026-09-12。代码基线 `2c11d16`，分支 `feature/electrobun-native-migration`。本次是调查，未修改产品代码。所有故障注入、GC 和实验性释放均运行于隔离副本；原开发实例和用户配置未重启、未改写。

## 结论

当前冷启动开发实例的私有工作集约 233–243 MiB，并未在这个实例中复现静止 400 MiB。此前安装版实测约 380 MiB，不能用当前冷启动数值否认之前的现象。

内容数量不能解释全部基础占用：不加载启动台的原生空窗口仍约 134 MiB；完整应用清空桌面内容后约 192 MiB；195 个应用、36 个文件夹的完整桌面约 251 MiB。原生设备恢复还会抬高后续静止占用，五次恢复后观察到约 327 MiB，而 JS 存活统计反而降低。

存在可核实的原生 WebGPU 引用释放缺口，但仅在旧设备退休时补充释放的实验没有消除主要增长。因此尚不能把这次恢复增长全部归咎于该缺口，也不能声称已经找到一个改动即可解决 400 MiB 的修复。

## 测量方法与口径

- 原实例 PID 40484，900×600、resolution=1、RTX 3060 Laptop、acrylic，桌面首页且无持续动画。后一次读取距最近呈现约 390 秒。
- 按 Windows `GetProcessMemoryInfo` 扩展计数读取私有工作集；另用 `VirtualQueryEx` / `QueryWorkingSetEx` 对驻留页归类。`process.memoryUsage().rss` 是总工作集，不能代替私有工作集。
- 每个内容对照使用独立进程，复制实际布局及图标/背景缓存到临时数据目录。实际布局为 195 个应用、36 个文件夹、3 页，顶层条目数 21/20/16。清空组同时关闭扫描根目录。
- 等待首屏和入场动画结束，再静置 8 秒采样；随后诊断 GC，分别再等 1 秒和 5 秒。恢复组每轮等待 8 秒，再执行 GC、等待 1.5 秒；末尾另静置 15 秒。采样为离散时刻，未声称捕获全部瞬时峰值。
- 表中内容配置对照通常各一次独立启动；数 MiB 差异只能当探索性信号。基础配置另外在恢复组得到约 248–252 MiB 的重复冷启动结果。
- `heapSize` / `heapCapacity` 都包含 `extraMemorySize`；后者包括字符串和 ArrayBuffer 等外部分配，不能重复相加。存活统计按最近一次 GC 解释。参见 [Bun HeapStats](https://bun.sh/reference/bun/jsc/HeapStats)。
- JS 逻辑容量、mimalloc 提交量、CPU 驻留页、GPU 专用/共享内存不是互斥分类，不能相加拼成一个精确占比饼图。

## 内容与配置对照

单位 MiB，取各独立进程的第一次静止私有工作集。

| 配置 | 私有工作集 | 图标 GPU 估算 |
|---|---:|---:|
| 完整实际配置 | 251.43 | 60.04 |
| 关闭后台图标预加载 | 244.29 | 50.02 |
| 在上一项基础上仅实现当前页 | 233.25 | 34.57 |
| 清空应用和文件夹、关闭扫描 | 192.41 | 0 |
| 完整配置，关闭 MSAA | 251.85 | 60.04 |
| 完整配置，解码图标最大边 128 | 246.54 | 15.02 |
| 完整配置，mimalloc purge delay=0 | 245.02 | 60.04 |

缩小纹理明显减少显存估算，对私有工作集的改善较小。仅当前页也仍有 1,390 节点、392 个 Text，当前页文件夹预览会访问 113 个图标。仅关闭后台预加载后仍有 163 个图标进入场景路径。因此预加载优化有收益，但无法解释或消除约 192 MiB 的应用底座。

这些实验没有进入产品：仅当前页会影响翻页准备策略；固定 128 会影响高 DPI/大图标质量；低 purge delay 的小幅差异未证明值得承担分配性能代价。

## 原生空窗口分阶段

相同运行时、900×600、透明、MSAA、默认独显；每个阶段诊断 GC 后采样。

| 阶段 | 私有工作集 MiB |
|---|---:|
| Bun worker 启动 | 26.61 |
| 导入 native host / Pixi | 37.50 |
| 创建窗口和 surface | 56.43 |
| requestAdapter 返回 | 49.53 |
| requestDevice 返回 | 116.76 |
| 创建 Pixi renderer 后 | 121.90 |
| 空窗口静止 | 134.47 |

`requestDevice` 阶段增加 67.23 MiB，同时 JS heapSize 仅从 5.63 到 5.66 MiB，Bun mimalloc 提交量从约 111.50 到 111.57 MiB。证据将该增量定位到设备创建的原生路径；尚不能在 Dawn、D3D12 runtime、用户态显卡驱动内部进一步精确分摊。

空窗口其他对照：关闭 MSAA 133.16 MiB，不透明 134.45 MiB，核显 144.39 MiB。当前机器上，没有发现通过这些开关大幅降低 CPU 私有工作集的办法。

## 设备恢复后的增长

原安装版日志中两次恢复均为 `system resume` / `mode=surface`，分别发生于 06:15:49.845Z 和 06:15:50.344Z，设备和 surface generation 从 1 变到 3。当前 `native-app.ts` 收到 resume 就请求 surface 恢复；恢复中收到请求会进入 pendingRecovery，结束后继续执行。是否同一唤醒周期的重复通知，应单独核实并合并。

隔离副本调用测试接口的 surface 恢复，走相同重建实现；这不是对真实 Windows 休眠/唤醒的完整复现。

| 五次恢复实验阶段 | 私有工作集 MiB | JS heapSize MiB |
|---|---:|---:|
| 恢复前静止 | 249.56 | 49.77 |
| 第 1 次恢复、GC 后 | 289.67 | 44.40 |
| 第 2 次恢复、GC 后 | 286.36 | 41.80 |
| 第 3 次恢复、GC 后 | 304.14 | 42.17 |
| 第 4 次恢复、GC 后 | 305.38 | 42.40 |
| 第 5 次恢复、GC 后 | 330.94 | 41.07 |
| 再静置 15 秒 | 327.02 | 41.06 |

所有这些样本均为 running、未最小化；场景保持 2,542 节点。恢复后后台预加载的非场景图标没有重新全部上传，驻留图标为 163 个，资源量并没有变得更多。增长不是严格每轮线性，释放/缓存时机也影响数值；五轮及 15 秒观察不能证明无限增长或永久不回收，但证明该入口值得优先处理。

另一次两轮实验从 245.95 到 297.06 MiB，末尾进一步回落至 283.67 MiB，也说明必须同时记录立即值和静置后的值。

## 原生引用释放审计与反证

已安装 Pixi 的 `PipelineSystem.destroy()`、`GpuShaderSystem.destroy()`、`BindGroupSystem.destroy()` 只清空 JS 缓存。Electrobun `webgpuAdapter.ts` 对 sampler、bind group/layout、shader module、pipeline 提供显式 `release()`；这些封装没有 GC finalizer，当前 compatibility 层也没有衔接 Pixi 的资源生命周期。设备 destroy 释放 queue/device 本身，不能据此推定外部创建引用都已释放。

诊断包装工厂函数，记录创建与显式释放，并在设备退休时进行二选一对照：仅计数，或补调所有仍持有包装对象的 release。两组均使用相同追踪结构，避免只把探针自身持有差异算成修复。

| 两轮恢复后的对照 | 仅追踪 | 退休时补 release |
|---|---:|---:|
| 恢复前静止 MiB | 249.60 | 247.45 |
| 第 1 次恢复、GC 后 MiB | 294.92 | 281.02 |
| 第 2 次恢复、GC 后 MiB | 302.23 | 290.91 |
| 再静置 15 秒 MiB | 300.12 | 293.66 |
| 相对各自起点的最终增量 MiB | 50.52 | 46.21 |

首个设备创建了 1,635 个 bind group、200 个 pipeline.getBindGroupLayout 返回包装、7 个 render pipeline、5 个 shader module 等；在退休前未观察到这些包装的 release 调用。大量 bind group 来自纹理 mip/准备路径，不能当作 1,635 个场景节点。

注意：首版审计的 `remaining` 表还包含 texture view 的包装；texture 的内部 `_releaseReference()` 可直接把 view.ptr 归零而绕过 public release 探针，因此不能把该表中的全部 texture view 当作未释放原生引用。后续探针源码已区分 ptr=0，本文不使用首版 view 计数证明泄漏。补 release 本身有 ptr=0 的幂等检查。

该释放缺口值得修复，但当前实验只改善了部分占用，最终增量相差约 4.3 MiB，无法解释整个恢复增长。不能把这份实验补丁直接视为已验证的产品修复；动态资源寿命、故障重试和其他平台仍需正式设计及回归。

## 建议顺序和剩余缺口

1. 继续追踪恢复前后存活的原生分配调用栈，区分 Dawn/驱动缓存、呈现/读回资源、仍未覆盖的引用。优先围绕 recover/device retirement 做 ETW/native heap 对照，而非继续只看 JS heap snapshot。WPR 工具已确认存在，本次未开启系统跟踪或修改 heap tracing 注册表。
2. 核实并合并同一 Windows 唤醒周期的重复恢复请求；完善原生 WebGPU 引用所有权。释放缺口已找到，但降低几十/上百 MiB 仍需用原生分配证据证明。
3. 再优化冷启动内容：按实际呈现范围预加载图标和相邻页，文件夹预览减少未使用节点，按显示像素尺寸选择图标纹理；静止基线另查应用模块/字体/Skia 的首次加载成本。

本次没有把 380–400 MiB 的全部来源精确分配到每个模块，也没有复现完整的原用户交互与休眠历史。已经确认的两条主线是约 134 MiB 的原生空窗口底座，以及设备恢复带来的额外非 JS 增长。
