# 混合图标驻留策略

2026-09-10，基线f4a3d17，Bun1.4.2 / Starter0.3.4。

## 已实现行为

原生启动不再解码整个布局。布局所有权由同步 `retain` 管理，与加载分离；共享Web仓库的
`synchronize`仍保持原来的等待加载语义。当前场景（含邻页、文件夹预览、拖拽与过渡）请求
图标时启动前台加载，最多4路。解码成功后主动通过当前renderer上传，随即释放CPU RGBA。
首次呈现前等待当前前台集合，完成后重新检查场景；后台无关解码不会阻止已经就绪的帧。

首个应用场景呈现后启动后台预热。每批以4MiB纹理像素预算和4ms时间预算限流，批间16ms；
单张解码不可抢占，至少允许完成一张，因此这些是软限制，不是硬实时承诺。后台每次解码
完成后检查前台请求，避免把所有冷图标预先排入队列挡住用户操作。暂停窗口时不推进预热。

图标GPU软预算为128MiB（RGBA含mipmap估算，不包括文字、背景、render targets或驱动开销）。
达到预算即停止投机解码；不能通过一边淘汰一边继续解码把整个布局扫完。前台需求可超预算，
随后按最近使用顺序卸载冷GPU纹理。当前场景引用，包括隐藏过渡引用，优先保护，允许受保护
集合或超大单图暂时超过软预算。编码恢复来源保留，未加载图片不占解码像素内存。

冷纹理重访与设备丢失使用已有编码快照恢复；原生renderer可能在异步解码期间改变，上传时
读取当前renderer。GPU GC缺失时发出标准unload通知重建绑定。布局移除/替换期间，仍被场景
引用的纹理不会提前销毁，最后场景引用消失后退休。这个保护修复了完整回归发现的
`textureSource.alphaMode`空source异常。用户显式重置图标会等待目标准备，不假报成功。

应用管理虚拟列表不再假定图标已全量加载：冷图标完成后原位更新该行图片，不重建整页；
回调只弱引用行节点，虚拟行销毁后不更新它。仓库在加载完成或销毁时清除一次性监听器。

开发诊断状态新增 `iconResidency`：预算、实际驻留图标纹理估算、驻留数和剩余后台队列。
队列清空也可能表示达到预算，并不表示全部布局已预热。

  后像素与原图逐字节一致；原device-lost/GPU GC/unload测试继续通过。
- 完整 `npm run native:smoke` 在重启恢复可访问桌面后通过（PID26028），含物理快捷键、

  已修复并用专项和完整回归重验。没有放宽原断言。
- 最终190/1000真实图案压力测试：首场景、首次远跳、连续快速反向跳页、后台预热、预算
  淘汰、设备丢失后重访均通过；恢复generation=2、recoveryCount=1，最终截图已检查。

“首次诊断”晚于首帧，后台已推进少量工作，故不是精确首屏最小图标数。1000组经过远跳后
共加载过937–1000张，但同时GPU驻留被预算限制；这不是后台一次性预热全部。恢复后只重建
再次使用的资源，因此驻留数不要求回到190/1000。

最终重启后测试分辨率为1.25倍（900×600逻辑尺寸，1125×750截图；重启前样本曾为2倍），经历多次翻页和设备恢复。
最终Windows私有驻留190组约371MiB、1000组约443MiB，包含测试历史/驱动/分配高水位，
不与此前DPI1首屏实验数字直接混比，也不承诺任务管理器固定降到某值。此次可验证目标是
去掉全量解码等待与闲置RGBA、限制图标GPU驻留并保留行为，不是RAM绝对值指标。

## 边界

首次进入未准备的内容仍需读取/解码/上传，可能暂停当前呈现；现有动画逻辑未替换，未使用
“先准备整个远跳路径”的过度预取。只有实际请求的场景资源进入前台集合。后台预热不是
零等待保证，预算也不是整个应用显存上限。128MiB是基于本轮190/1000测试的初始实现值，
后续若需要用户可配或设备感知预算，应单独验证，当前不增加设置项。

证据：`.codex-dev/residency-check-complete.log`、`residency-smoke-scene-lease.log`；
`.codex-dev/residency-test/run-{190,1000}-reboot-final`的samples/proof/memory JSON及截图。
调查阶段报告另见native-icon-upload-strategies.md，不将实验数据当正式版本保证。
