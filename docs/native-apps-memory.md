# 应用列表虚拟化与内存对照

日期：2026-09-06。基线：`f104403`，本轮首先加入测量入口，记录优化前结果，再接入虚拟列表。测试使用独立原生运行目录和隔离数据，不修改用户布局。

## 测量条件

- 固定1000条合成应用，URL目标，不主动加载1000份图片；740×450列表视口。
- 同一机器与Starter0.2.13，原生WebGPU运行；每个版本独立启动进程。
- 6轮打开1000条、搜索为100条、选择后显示1000条、销毁列表；记录构建时间、节点数、RSS和JavaScriptCore堆。
- 每个阶段等待实际呈现；轮末等待100ms。最后记录一次显式GC前后值，仅用于诊断，不改变生产GC策略。
- 两版使用相同测量流程。RSS是整个进程工作集，不是JS堆或独占物理内存；本次没有GPU显存和私有提交分项采样。

## 本机结果

| 指标 | 优化前 | 虚拟化后 |
| --- | ---: | ---: |
| 首次打开显示节点 | 18,042 | 176 |
| 首次构建耗时 | 267.4ms | 11.2ms |
| 首次打开RSS | 924.5MiB | 418.2MiB |
| 6轮中最大RSS | 2100.7MiB | 463.7MiB |
| 最后诊断GC后RSS | 1615.8MiB | 412.1MiB |
| 最后诊断GC后JS堆 | 797.0MiB | 65.1MiB |

虚拟化后六轮关闭阶段RSS分别456.4、424.5、438.6、416.4、440.4、446.9MiB。此短测试未出现优化前的同量级单调增长，但不能据此保证长时间没有泄漏。优化前保留对象的具体归属尚未做堆快照分析；不把整个差值都归因于单一缓存或泄漏。

原始结果：`artifacts/apps-memory-before.json`、`artifacts/apps-memory-after.json`。日志在`.codex-dev/apps-memory-before.log`与`apps-memory-after.log`。测量入口`src/native/nativeAppsMemoryBenchmark.ts`通过`LAUNCHPAD_MEMORY_BENCH=<绝对JSON路径>`启用；用`--dev --isolated --settings-only --runtime=<独立运行目录>`运行现有runner。独立目录必须先以当前源代码构建，并指向新数据服务；现有`.codex-dev/build-settings-runtime.ts`仅是本机打包辅助，不是发行工具。不得用普通用户数据运行合成基准。

## 实现与边界

上述测量版本中，应用管理、排除列表和扫描结果按固定78px行距计算可见范围，上下各保留2行缓冲；离屏行销毁，键盘聚焦行保留。逻辑选择存在共享应用核心，虚拟控件通过稳定应用ID恢复焦点。键盘控件描述仍为O(N)轻量对象；显示节点与GPU绘制资源约为O(可见行数)。搜索/选择仍会重建当前可见行，尚未做行内容增量更新。

随后应用页样式对齐将列表改为64px行高+6px间距，并使用独立列表滚动，固定上方搜索与操作区。上表保留先前78px行距版本的实测记录，未作为此次样式修改后的重新测量结果；当前代码运行基准时应另存结果再比较。

宿主滚动位置和展开条动画把实际viewport传入列表；行转移显式保留原子节点顺序，避免当前Pixi removeChildren返回逆序后背景覆盖复选框。控件测试覆盖1000条跨屏焦点与回收，实际GPU继续验证多选、实时搜索、排除恢复、扫描添加和持久保存。

下一阶段：实际190/1000/5000应用和图片数据集、较长开关循环、私有提交/JS堆快照/GPU纹理预算；按需创建折叠的外观预览，以及可见行增量更新。当前结果不能直接承诺用户主实例的300MB会降到某个固定数值。
